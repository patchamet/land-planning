# ADR-0001 — จะเก็บข้อมูลไว้ที่ไหน

> **สถานะ: 🟢 ตัดสินใจแล้ว — เลือก B (IndexedDB + PWA)**
> วันที่เสนอ: 2026-08-08 | วันที่ตัดสิน: 2026-08-08
> เกี่ยวข้องกับ: [02-container.md](../02-container.md)

---

## บริบท

ระบบบันทึกการทดลอง ([01-context.md](../01-context.md)) ต้องเก็บข้อมูลไว้ที่ไหนสักที่
เป็นการตัดสินใจที่ **กลับยากที่สุด** ในระบบ เพราะกำหนดทั้งวิธีใช้งานประจำวัน ความเสี่ยงข้อมูลหาย และเส้นทางไป Phase 3

**สิ่งที่ต้องรู้ก่อน: ข้อมูลชุดนี้คือสินทรัพย์ทั้งหมดของโปรเจกต์**
โรงเรือนสร้างใหม่ได้ พืชปลูกใหม่ได้ แต่ข้อมูล 2 ปีที่บันทึกไว้ ถ้าหายคือกลับไปเริ่มนับหนึ่ง และเป็นสิ่งเดียวที่ทำให้ Phase 5 ตัดสินใจขยายได้อย่างมีเหตุผล

---

## เกณฑ์ตัดสิน (เรียงตามความสำคัญ)

| # | เกณฑ์ | ทำไม |
|---|---|---|
| 1 | **กรอกได้ตอนไม่มีเน็ต** | สัญญาณในโรงเรือนกลางที่ดินไม่แน่นอน — ถ้ากรอกไม่ได้แม้ครั้งเดียว ความเชื่อมั่นจะหายทันที |
| 2 | **ข้อมูลไม่หาย** | ดูย่อหน้าข้างบน |
| 3 | **กรอกเร็ว ≤15 วินาที** | ข้อจำกัดหลักจาก [01-context.md](../01-context.md) §4 |
| 4 | **เก็บรูปถ่ายได้** | รูปคือข้อมูลที่มีค่าที่สุดต่อวินาทีที่ใช้กรอก (ถ่าย 1 รูป = ข้อมูลที่พิมพ์ 5 นาทีก็ไม่ครบ) |
| 5 | **Phase 3 ให้ sensor เขียนเข้าได้** | ดูข้อสังเกตสำคัญด้านล่าง |
| 6 | **มือถือกับคอมเห็นข้อมูลเดียวกัน** | กรอกที่โรงเรือน วิเคราะห์ที่บ้าน |
| 7 | **ไม่มีอะไรให้เน่า / ค่าใช้จ่ายต่ำ** | โปรเจกต์ส่วนตัวระยะยาว ไม่มีใครมาดูแลแทน |

### ⚠️ ข้อสังเกตสำคัญเรื่องเกณฑ์ที่ 5

**sensor เขียนข้อมูลลง localStorage หรือ IndexedDB ไม่ได้** — สองอันนั้นอยู่ใน browser ต้องมีคนเปิดหน้าเว็บถึงจะมีตัวตน แต่ sensor ส่งข้อมูลตอนตี 3 ที่ไม่มีใครเปิดอะไรเลย

แปลว่า **ถ้าไปถึง Phase 3 จริง ยังไงก็ต้องมีที่เก็บข้อมูลฝั่ง server** ไม่ทางใดก็ทางหนึ่ง

คำถามจึงไม่ใช่ *"เอา server ไหม"* แต่คือ **"เอา server ตอนนี้เลย หรือรอถึงตอนนั้น"** — และคำตอบขึ้นกับว่าจะไปถึง Phase 3 จริงไหม ซึ่งตอนนี้ยังไม่รู้ (Phase 2 คือ gate ที่คนตกมากที่สุด ตาม [00-concept.md](../00-concept.md) §7)

## ตัวเลือก

### A — localStorage

| ✅ ข้อดี | ❌ ข้อเสีย |
|---|---|
| ง่ายที่สุด เขียนโค้ดไม่กี่บรรทัด | **จำกัด ~5MB → เก็บรูปไม่ได้เลย** (ตกเกณฑ์ 4) |
| ออฟไลน์ 100% | เป็น string ล้วน ต้อง JSON.parse ทั้งก้อนทุกครั้ง |
| ไม่มีค่าใช้จ่าย | ช้าลงเรื่อยๆ เมื่อข้อมูลโต |
| | มือถือ/คอม แยกกันสิ้นเชิง |

**สรุป:** ตกที่เกณฑ์ 4 อย่างเดียวก็พอ — 5MB คือรูปถ่ายมือถือประมาณ 2 รูป

---

### B — IndexedDB + PWA ⭐ *เสนอ*

| ✅ ข้อดี | ❌ ข้อเสีย |
|---|---|
| **เก็บรูปได้จริง** (เก็บ blob ได้ พื้นที่ระดับ GB) | มือถือกับคอมยังไม่ sync กัน (ตกเกณฑ์ 6) |
| ออฟไลน์ 100% | API ยุ่งกว่า localStorage พอสมควร |
| **ติดตั้งลง home screen ได้** → เปิดเร็วเหมือนแอป ตรงกับเกณฑ์ 3 | sensor เขียนเข้าตรงๆ ไม่ได้ (แต่ Phase 3 ค่อยแก้) |
| ไม่มีค่าใช้จ่าย ไม่มี vendor | มีความเสี่ยงเรื่องข้อมูลถูกล้าง (ดูด้านล่าง) |
| query ตามช่วงเวลา/แปลงได้เร็ว | |

**ความเสี่ยงที่ต้องรู้:** browser อาจล้างข้อมูลได้เองเมื่อพื้นที่เครื่องเต็ม และ **Safari บน iOS มีนโยบายลบข้อมูลเว็บที่ไม่ได้เปิดนานหลายวัน** — การติดตั้งเป็น PWA ลง home screen ช่วยลดความเสี่ยงข้อนี้ได้มาก *(ควรทดสอบจริงบนเครื่องที่จะใช้ ก่อนพึ่งพาเต็มตัว)*

**การป้องกัน:** export JSON อัตโนมัติทุกสัปดาห์ + เตือนถ้าไม่ได้ export เกิน 14 วัน

---

### C — Backend จริง (Supabase / PocketBase)

| ✅ ข้อดี | ❌ ข้อเสีย |
|---|---|
| **มือถือ + คอม เห็นข้อมูลเดียวกัน** | ต้องทำ offline-first + sync เองอยู่ดี (ไม่ใช่ของฟรี) |
| **sensor เขียนเข้าได้ตรงๆ ใน Phase 3** | มี auth, มี vendor, มี migration, มีบิล |
| ข้อมูลไม่หายไปกับเครื่อง | ถ้าเน็ตล่มแล้วไม่ได้ทำ offline ไว้ = กรอกไม่ได้ (ตกเกณฑ์ 1) |
| หลายคนใช้ได้ (Phase 4) | **งานเพิ่มขึ้น 2–3 เท่าตั้งแต่วันแรก** ทั้งที่ยังไม่รู้ว่าจะไปถึง Phase 3 ไหม |

**สรุป:** ถูกในระยะยาว แต่แพงเกินไปตอนนี้ — เป็นการจ่ายราคาของ Phase 3 ตั้งแต่ Phase 2 ทั้งที่ Phase 2 ยังไม่ผ่าน

---

### D — Google Sheet เป็นฐานข้อมูล

| ✅ ข้อดี | ❌ ข้อเสีย |
|---|---|
| เห็นข้อมูลดิบได้ตลอด แก้มือได้ ทำกราฟเองได้ | **ต้องมีเน็ตเสมอ** (ตกเกณฑ์ 1 ซึ่งเป็นเกณฑ์อันดับ 1) |
| ข้อมูลอยู่บน Drive ไม่หาย | ช้า — เขียนแต่ละครั้งใช้เวลาเป็นวินาที (ตกเกณฑ์ 3) |
| ไม่มีค่าใช้จ่าย | เก็บรูปลำบาก |
| แชร์ให้คนอื่นดูง่าย | โครงสร้างข้อมูลจะเพี้ยนเมื่อมีคนไปแก้มือ |

**สรุป:** ตกเกณฑ์อันดับ 1 และ 3 — แต่ **เหมาะมากในฐานะปลายทางของ export** ไม่ใช่ฐานข้อมูลหลัก

---

### E — ไฟล์ JSON ใน git repo

| ✅ ข้อดี | ❌ ข้อเสีย |
|---|---|
| มีประวัติทุกการเปลี่ยนแปลงฟรี | **กรอกจากมือถือแทบเป็นไปไม่ได้** (ตกเกณฑ์ 1, 3) |
| ข้อมูลอยู่กับโค้ด ย้อนดูได้ | ไฟล์เดียวโตขึ้นเรื่อยๆ merge conflict ง่าย |
| ไม่มีค่าใช้จ่าย | เก็บรูปใน git = repo บวม |

**สรุป:** ไม่เหมาะเป็นที่เก็บหลัก แต่ **เหมาะเป็นที่เก็บ "ข้อมูลตั้งต้น"** ที่เปลี่ยนไม่บ่อย เช่น รายการพืช รายการชนิดค่าที่วัด

## การตัดสินใจ

**เลือก B — เก็บข้อมูลในเครื่อง (IndexedDB) + ทำเป็น PWA** โดยมีเงื่อนไข 3 ข้อ:

1. **แยกโค้ดส่วนเก็บข้อมูลออกมาเป็นโมดูลเดียว** — ส่วน UI ห้ามเรียก IndexedDB ตรงๆ ให้เรียกผ่านฟังก์ชันกลางเท่านั้น (`saveEvent`, `listReadings`, …) เพื่อให้เปลี่ยนไปใช้ backend ใน Phase 3 ได้โดยแก้ไฟล์เดียว

   *(ปกติผมจะเตือนว่านี่คือ over-engineering — แต่เคสนี้เรารู้แน่ๆ อยู่แล้วว่าจะต้องเปลี่ยน และมันเป็นโค้ดแค่ไฟล์เดียว จึงคุ้ม)*

2. **Export/Import JSON เป็นฟีเจอร์ระดับ v1** ไม่ใช่ของที่ค่อยทำทีหลัง — พร้อมคำเตือนถ้าไม่ได้ export เกิน 14 วัน

3. **ทดสอบเรื่องข้อมูลถูกล้างบนมือถือเครื่องที่จะใช้จริง** ก่อนเริ่มเก็บข้อมูลจริงจัง

**และเปิด ADR-0002 ไว้สำหรับ Phase 3** — ตอนนั้นค่อยตัดสินใจเรื่อง backend โดยมีข้อมูลจริงว่าใช้งานยังไง ข้อมูลโตแค่ไหน ซึ่งตอนนี้เดาไม่ได้

### ทำไมไม่เลือก C ทั้งที่รู้ว่ายังไงก็ต้องใช้

เพราะ **เกณฑ์อันดับ 1 คือกรอกได้ตอนไม่มีเน็ต** ซึ่งแปลว่าต้องทำ offline-first ไม่ว่าจะเลือกอะไร
เมื่อต้องทำ offline-first อยู่แล้ว การเพิ่ม backend เข้าไปตอนนี้จึงได้แค่ "sync" มาอย่างเดียว โดยแลกกับงานอีก 2–3 เท่า auth vendor และบิลรายเดือน — **ในขณะที่ยังไม่รู้ด้วยซ้ำว่าจะผ่าน Phase 2 ไหม**

ถ้าผ่าน Phase 2 ได้ (ปลูกครบ 3 รอบ บันทึกต่อเนื่อง ไม่หมดไฟ) ตอนนั้นการลงทุนทำ backend จะมีเหตุผลรองรับ และจะรู้ด้วยว่าต้องการอะไรจริงๆ

## ผลที่ตามมา

**ได้:**
- เริ่มเขียนโค้ดได้ทันที ไม่ต้องตั้ง server ไม่ต้องสมัครอะไร
- ใช้งานได้แม้เน็ตล่ม
- เก็บรูปได้เต็มที่
- ต้นทุน 0 บาท ไม่มี vendor ผูกมัด

**เสีย / ต้องยอมรับ:**
- มือถือกับคอมเป็นคนละชุดข้อมูล → ต้อง export/import ด้วยมือถ้าจะย้าย
- ต้องมีวินัย export สำรอง (ระบบต้องช่วยเตือน ไม่ใช่พึ่งความจำ)
- Phase 3 ต้องทำงานเพิ่มเรื่อง sync — แต่จำกัดอยู่ในโมดูลเดียวตามเงื่อนไขข้อ 1

**ทางลดความเสียหาย:** ถ้าเรื่อง "มือถือ/คอมไม่ sync" กวนใจเร็วกว่าที่คิด สามารถเพิ่มการ export ขึ้น Google Drive อัตโนมัติได้โดยไม่ต้องเปลี่ยนสถาปัตยกรรม — เป็นทางออกกลางทางที่ราคาถูกกว่าการทำ backend เต็มรูปแบบมาก

## ข้อสมมติที่ตั้งไว้ตอนตัดสินใจ

การตัดสินใจนี้ตั้งอยู่บนข้อสมมติ 3 ข้อ ถ้าข้อไหนไม่จริง ต้องกลับมาทบทวน:

| # | ข้อสมมติ | ถ้าไม่จริงจะเกิดอะไร |
|---|---|---|
| 1 | กรอกข้อมูลจากมือถือเป็นหลัก | ถ้ากรอกจากคอมเป็นหลัก PWA/offline จะไม่จำเป็น และควรพิจารณา D หรือ E ใหม่ |
| 2 | มือถือกับคอมเป็นคนละชุดข้อมูลได้ในปีแรก | ถ้ารับไม่ได้ → เพิ่ม auto-export ขึ้น cloud drive ก่อน ยังไม่ต้องถึงขั้นทำ backend |
| 3 | ปีแรกมีคนกรอกคนเดียว | ถ้ามีคนอื่นกรอกด้วย → ข้ามไปตัวเลือก C ทันที เพราะ export/import ด้วยมือระหว่างหลายคนใช้ไม่ได้จริง |

## เงื่อนไขที่จะทำให้กลับมาทบทวน ADR นี้

เปิด **ADR-0002** เมื่อเกิดข้อใดข้อหนึ่ง:

- ผ่าน Phase 2 แล้ว (ปลูกครบ 3 รอบ บันทึกต่อเนื่อง) และตัดสินใจเดินหน้า Phase 3
- มีคนที่ 2 ต้องกรอกข้อมูล
- เจอปัญหาข้อมูลถูก browser ล้างจริง ไม่ใช่แค่ความเสี่ยงบนกระดาษ
- ต้องส่งข้อมูลให้คนนอก (ผู้รับซื้อ / นักวิชาการเกษตร) เห็นเป็นประจำ
